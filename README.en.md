## What you get

Once installed you can just ask the AI "what's the bot's balance?" or "what state is it in?",
instead of digging through logs. And the admin can send `#功能 balance off` in QQ to turn a query
off — it takes effect immediately, no file editing, no restart.

Here is what you can look up:

| Query | What comes back |
| --- | --- |
| Runtime | current mode, whether DSH is ready, the allowlist, the owner, unread count and wake state per conversation |
| Balance | how much is left, how fresh that number is, the alert threshold, and how long until it actually shuts down |
| Reasoning tier | which tier is active right now. The schedule switches to the cheaper tier during DeepSeek's billing peak and back to the good one off-peak, which saves a bit of money |
| Holiday table | whether the table still covers you; when a year is missing you can pull the State Council notice and see what it would parse to |
| Greetings | which personas have a startup/shutdown line configured, and where those go |
| Admin commands | triggers and permission rules for `#余额` `#关机` `#功能` `#帮助` |
| Bridge config | the config itself, with tokens masked |

## How it works inside

None of the decision logic is re-implemented here. Billing peak/off-peak, holiday parsing, wake
filtering and balance alerts are all `import`ed straight from qq-bridge's own pure modules. The
plugin only fetches data and formats text.

```
qqbridge-plus  ──import──▶  qq-bridge/src/wake-filters.mjs   (billing / holidays / wake / balance)
               ──import──▶  qq-bridge/src/whale-balance.js    (balance ledger)
               ──HTTP────▶  qq-bridge console 127.0.0.1:3100  (runtime: mode, sessions, tier)
               ◀──HTTP────  QQ admin commands forwarded by qq-bridge
```

The reason is that qq-bridge is the authority on the QQ side: the SnowLuma connection, the
allowlists, session mapping and timers all live in its process. A second copy of the decision logic
would drift from the first sooner or later, and during development it actually did. With a `NaN`
balance, one side judged `recovered` while the other judged `none` — and that is the branch that
decides whether to shut the bot down. The feature-key list works the same way: the bridge does not
keep its own copy, otherwise the plugin adds a feature and the bridge starts rejecting a perfectly
valid command first.

When the bridge is not running the plugin does not throw. The tool tells you the console is
unreachable and how to go about checking it.

## Installing it

### 1. Prerequisites

| Needed | Why |
| --- | --- |
| Node.js ≥ 18 | required by both DSH and qq-bridge |
| git | to clone this repo (skippable for a manual install from a zip) |
| [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) | the plugin host. Must have been **started at least once**, otherwise the profile directory does not exist yet |
| [qq-bridge](https://github.com/Derpyu520/qq-bridge) | the plugin `import`s its pure modules and calls its endpoints, so it must be installed first |

> You do not need to tell the installer where qq-bridge is: by default it looks for a `qq-bridge`
> directory next to the plugin. If that is not where yours lives, pass `--bridge-dir`.

### 2. Install

#### Option A: automated (recommended)

**Dry-run first** to see exactly what it would change (worth doing the first time):

```bat
node "%USERPROFILE%\dsh-plugins\qqbridge-plus\scripts\install.mjs" ^
     --dir "%USERPROFILE%\dsh-plugins\qqbridge-plus" --dry-run
```

Drop `--dry-run` once it looks right. Full flow (clone plus install):

**Windows (cmd or PowerShell)**

```bat
git clone https://github.com/xueyingneko/qqbridge-plus.git "%USERPROFILE%\dsh-plugins\qqbridge-plus"
node "%USERPROFILE%\dsh-plugins\qqbridge-plus\scripts\install.mjs" --dir "%USERPROFILE%\dsh-plugins\qqbridge-plus"
```

**Linux / macOS / Git Bash**

```bash
git clone https://github.com/xueyingneko/qqbridge-plus.git ~/dsh-plugins/qqbridge-plus
node ~/dsh-plugins/qqbridge-plus/scripts/install.mjs --dir ~/dsh-plugins/qqbridge-plus
```

**If qq-bridge is not next to the plugin**:

```bat
node "...\scripts\install.mjs" --dir "...\qqbridge-plus" --bridge-dir "D:\path\to\qq-bridge"
```

**To install into the web profile instead of desktop**: add `--profile web`.

**Already inside the repo?** The wrapper script figures that out on its own:

```bat
scripts\install.cmd --dry-run
```

What the installer does — every step is idempotent, so re-running writes nothing twice:

1. clones the repo, or runs `git pull` on an existing one;
2. installs the single npm dependency, `@deepseek-ai/schemastery`, in the plugin directory;
3. registers the package in the profile's `package.json`: a `link:` entry under `dependencies`,
   and the package name appended to `dsh.profile.bundles`;
4. appends the plugin entry to the profile's `cordis.patch.yml` (skipped if already present);
5. has the package manager create the `node_modules` link inside the profile (pnpm preferred, to
   match the profile's own lockfile);
6. checks whether qq-bridge is in place and prints the next steps.

Profile files are backed up before being modified, as `package.json.bak-<timestamp>`, and writes
go through a temp file plus rename so another process can never read a half-written file.

**Uninstall**: remove `dsh-plugin-qqbridge-plus` from `dependencies` and `dsh.profile.bundles` in the
profile's `package.json`, delete the entry carrying the
`# === dsh-plugin-qqbridge-plus (managed by install.mjs) ===` marker from `cordis.patch.yml`, and
restart DSH.

#### Option B: manual

Use this if you want fine control (managing the symlink yourself, installing into several profiles).

**Step one, register in the profile**: add the package to
`~/.dsh/profiles/<profile>/package.json` under `dependencies` (with `link:` pointing at this
repo), and to `dsh.profile.bundles` as well:

```json
{
  "dependencies": {
    "dsh-plugin-qqbridge-plus": "link:/abs/path/to/qqbridge-plus"
  },
  "dsh": {
    "profile": {
      "bundles": ["...", "dsh-plugin-qqbridge-plus"]
    }
  }
}
```

Then run `pnpm install` (or `npm install`) in the profile directory to create the link.

**Step two, add an entry to the profile's `cordis.patch.yml`**:

```yaml
- id: qqbridge-plus
  name: dsh-plugin-qqbridge-plus
  config:
    bridgeDir: '/abs/path/to/qq-bridge'   # ← point at your qq-bridge checkout
    consoleBase: 'http://127.0.0.1:3100'
    personaSection: true
    sectionOrder: 7
    features:
      status: true
      balance: true
      schedule: true
      holidays: true
      greeting: true
      commands: true
      config: true
```

The `id` must be `qqbridge-plus` (DSH uses the entry id to locate the settings namespace) and the
`name` must be the package name.

Step two is not optional. A bundle's own `cordis.patch.yml` only describes which rows that bundle
carries; the profile-level patch is what makes the loader create the entry. With step one only,
the plugin manager reports `installed=true` and lists the row, yet the tool does not exist at all
— and no error is printed.

**Step three, restart DSH.**

### 3. Verify it installed

After restarting DSH, either of these will tell you:

- ask the AI for the bot's status — it should reach the `qqbridge` tool;
- or look at `state/plugin-apply.json` in the bridge directory, whose `trace` records this assembly:

  ```json
  { "trace": [ { "phase": "apply-called" }, { "phase": "tool-registered" },
               { "phase": "http-api-registered" }, { "phase": "apply-returned" } ] }
  ```

  A trace that stops at `apply-called` means assembly failed partway; no file at all means the
  plugin was never loaded.

### 4. Enable QQ-side toggling (optional)

In qq-bridge's `config.json`:

```json
"featureCommand": {
  "triggers": ["#功能", "#开关"],
  "baseUrl": "http://127.0.0.1:19387"
},
"helpCommand": { "triggers": ["#帮助", "#help"] }
```

`baseUrl` points at the DSH web server, where the plugin endpoint is mounted. Then restart
qq-bridge.

## Usage in QQ (admin only)

```
#帮助                     list all admin commands (triggers rendered from current config)
#功能                     show all toggles (values changed from QQ are marked *)
#功能 balance off         disable a feature (also 关 / 禁用 / off / 0)
#功能 balance 开          enable (also 启用 / on / 1)
#功能 reset               clear runtime overrides, back to the config file values
```

- Triggers are configurable (`featureCommand.triggers` / `helpCommand.triggers`).
- The help text is assembled from the configured triggers, so it follows any change you make and
  can never contradict your setup.
- Admin only (qq-bridge's `ownerQQ`). With no `ownerQQ` configured these commands are unusable
  for everyone.

## The switches

One boolean per feature, `false` means off, with `'*'` as a fallback. All on by default.

Precedence:

```
QQ / runtime override file  >  composition config  >  code default (all on)
```

In other words, what was changed in QQ beats what is written in the config. Overrides live in
`qq-bridge/state/plugin-features.json`, written atomically (temp file plus rename) so another
process can never read half a JSON. They survive a DSH restart, and `#功能 reset` clears them.
A corrupt state file is treated as "no overrides" and the reason is recorded; it never stops the
plugin from starting.

### What happens when a feature is off

- The action stays in the enum and answers with a clear sentence rather than being removed:

  ```
  ⛔ 功能「余额与自动关机」已在插件配置里关闭。
  当前开启的功能：status（总览）、schedule（计费峰谷与推理档位）…
  ```

  It is not removed from the enum because the tool schema is serialized at `defineTool()` time and
  cannot be added to or removed from afterwards. Rather than fake "the config changed but the enum
  didn't", the off state is left visible.

- The matching section in `status` states the reason: `⛔ 已关闭（features.balance=false）`.
- The system prompt is generated from the toggles, so disabled features are not advertised and
  the model does not waste an attempt on them.
- A misspelled toggle name is reported and recorded in `plugin-apply.json`'s trace. The usual
  trap with this kind of switch is writing `scheduler` instead of `schedule`, which looks like
  "set but not working".

## Three hard rules

All learned the hard way. Worth reading before changing the code.

### 1. `inject` must list every service you will touch

Cordis throws when you access a service property that was not declared in `inject`:

```
Error: cannot get property "systemPrompt" without inject
```

Only `tools` was declared at first, with `if (ctx.systemPrompt)` intended as an
optional-dependency fallback — but reading the property itself throws, so the fallback never
runs. In the plugin manager this shows up only as `[failed]` or "did not activate", with no
reason given.

### 2. Do not export `Config` unless it is a real schemastery schema

When the loader sees a `Config` export it validates against it and expects it to come from
`@deepseek-ai/schemastery`. A plain object fails before `apply` ever runs (the entry is created,
`apply` does not execute a single line). And schemastery is a bare specifier: if the plugin
directory has no `node_modules` of its own it cannot be resolved, and the whole module fails at
import time.

There is a second measured boundary: `volatile` fields make the loader evaluate the config into
`{}`. A writable DSH settings panel requires `volatile`, but measurement (raw evidence kept in
`lib/last-apply-config.json`) showed that after evaluation every volatile field becomes `{}`, so
`sectionOrder` is no longer a number and `order must be a finite number` makes the plugin vanish
entirely. Even bypassing that, pressing Save in the settings panel would corrupt the config. So
this plugin's settings panel is read-only, and changing switches is done through QQ commands or
the config file. A test asserts this stays true.

### 3. `defineTool` must be a top-level static import

`lib/index.js` uses a static import with a hard-coded absolute path, the same approach official
plugins take. The first attempt used a runtime dynamic `import()` with 7 fallback paths for
"safety", and produced the hardest failure of all: one path reported import success, yet the
`.then()` on the chain never ran — no throw, no catch — so the tool was simply never registered.

A plain node subprocess cannot read inside `app.asar`, so this module cannot be imported by plain
node. That is an Electron asar property, not a defect; use the tests under `test/`, which do not
import that file.

**Self-check for troubleshooting**: assembly writes `qq-bridge/state/plugin-apply.json`, whose
`trace` array records how far it got. The host console is invisible in the GUI and loader startup
failures give no reason, so this file is the only judge that requires no guessing.

## Version pairing

The plugin and qq-bridge are a cross-repo dependency. qq-bridge reports both versions at startup:

```
[bridge] 版本：qq-bridge 0.2.0
[bridge]       插件：dsh-plugin-qqbridge-plus 1.0.0
```

Each side takes its version solely from its own `package.json` `version`, with no second copy.
Also learned the hard way: a version constant was once hard-coded in a module and contradicted
`package.json`, which amounts to having no trustworthy version at all.

## Tests

```bash
npm test                                             # plugin side: 52 + 21
node ../qq-bridge/scripts/test-feature-command.mjs   # bridge pure functions: 28
node ../qq-bridge/scripts/e2e-feature-command.mjs    # end-to-end: 10 (both sides running)
```

CI runs only the two suites that do not need qq-bridge (52 + 21). The two that need a running
bridge stay local — a CI that always fails is worse than no CI.

Key safety and correctness assertions:

| Assertion | Why it matters |
| --- | --- |
| `config` summary must not contain an unredacted `accessToken` | model context is retained long-term |
| A misspelled toggle must not disable any feature | "set but not working" is the hardest to diagnose |
| No field may carry `volatile` | it makes the loader evaluate config into `{}`, corrupting it on save |
| The endpoint must reject or not register without a token | it can widen the entire tool surface |
| `#功能xyz` must not be treated as a command | a false positive swallows ordinary chat |
